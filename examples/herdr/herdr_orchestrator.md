# Herdr 운용 규칙 (하네스 운영 문서)

이 문서는 **어떻게** 워커를 띄우고, 기다리고, 거두는지만 다룹니다. 무엇을 누구에게 언제 시키고 어떻게 검증·수락하는지는 `.routing/ROUTING_POLICY.md`가 정하며, 이 문서가 그것과 어긋나면 정책이 우선합니다(AUTH-7). 아래에서 규칙 ID는 그 정책을 가리킵니다.

## 1. 시작 전 점검
- 현재 Herdr 서버·세션에서 사용 가능한 워커, pane, 작업 디렉토리를 확인한다.
- 역할별 harness/model/effort는 `python3 .routing/resolve_models.py --role <id>`로 해석해 pane을 띄울 때 명시한다(MODEL-1). 해석 결과가 비어 있는 필드는 인자를 생략하고 하네스 기본값을 쓴다. `opencode` 하네스는 반드시 TUI 환경에서 시작한다.
- 해당 역할에 필요한 도구(파일 읽기·검색, researcher는 웹 접근)가 pane에 있는지 먼저 확인한다(`evidence_orders.tool_preflight`). 없으면 그 역할은 BLOCKED이고, 호스트가 대신 기억으로 답하지 않는다(EVID-7).

## 2. 워커 재사용과 분할
- 새 작업에는 기존 pane을 재사용해도 된다. 단, **자기 산출물을 검토하는 데는 절대 재사용하지 않는다**(ROLE-7).
- 구현 작업은 독립적으로 움직일 수 있는 조각일 때만 나눈다. 하나의 implementer로 끝낼 수 있으면 하나만 쓴다. 이 "최소화"는 구현 워커에만 해당하며, 워크플로가 요구하는 검토자·테스터 수는 줄이지 않는다(WF-2, WF-3).
- Git 저장소에서 동시에 쓰는 워커들에게는 각각 별도 worktree를 준다. 두 작성자가 체크아웃을 공유하지 않는다(SAFE-4).

## 3. 지시 전달
- pane에 보내는 것은 작업 지시서 하나다: `templates.work_order`의 필수 필드(목표, 수용 기준, 입력 참조와 버전, 읽기/쓰기 범위, 허용 행동, 제약과 재량, 중단 조건, 산출물, 보고 경로)와 관련 verification_plan 항목, 공유 제약만 보낸다(ORDER-2). 정책 전문·이 문서·호스트 프롬프트는 보내지 않는다(ENF-7).
- 조사 역할(inspector/researcher)은 `evidence_orders.order_defaults`를 쓴다: 대상 저장소는 읽기 전용, 쓰기는 `.routing/evidence/<order_id>.json` 하나(ORDER-7).
- 워커에게 "다른 pane에 전달해 달라"고 시키지 않는다. 모든 전달은 호스트가 한다(AUTH-2).

## 4. 대기와 생존 확인 (ORDER-8)
- 위임한 뒤에는 pane의 신호를 기다린다. 신호는 `RESULT_SUBMITTED`, `NEEDS_DECISION`, `BLOCKED`, 또는 heartbeat 타임아웃 네 가지다.
- 신호 없이 600,000 ms가 지나면 pane 상태(실행 중인지, 종료됐는지)를 확인한다. 두 번 연속 무응답이면 그 지시서를 BLOCKED로 기록하고 재발행하거나 사용자에게 올린다.
- 보고 없이 종료된 워커는 **결과를 제출한 것이 아니다.** 남은 산출물을 수락하지 않고, 진단 목적으로만 들여다본 뒤 새 revision으로 재발행한다(AUTH-5).
- 기다리는 동안 호스트가 할 수 있는 일: 워커의 `NEEDS_DECISION`에 답하기(Q-2), 읽기 전용 조사·자문 지시서 발행, 이미 돌아온 보고서·아티팩트 검사, 상태 기록. 할 수 없는 일: 제품 코드 수정, 같은 자원에 두 번째 작성자 투입, 작업 수락.

## 5. 보고서 처리
- 워커의 보고서는 짧아야 한다: 결과, 커밋 또는 아티팩트 위치, 검증 결과, 미해결 문제. 전체 로그는 메인 대화에 넣지 않는다.
- 보고서를 읽은 뒤 반드시 실제 diff·스크린샷·아티팩트를 직접 검사한다. 완료 메시지나 검토자 PASS는 수락의 입력이지 수락이 아니다(AUTH-5, VER-7).
- 독립 검토가 필요하면 그 변경을 작성·옹호하지 않은 **다른 세션**의 워커에게 특정 커밋/아티팩트 버전을 고정해 검사시킨다. 다른 모델이면 더 좋지만 그것만으로 독립성이 되지는 않는다(ROLE-7).
- 사실 불일치는 테스트나 검증 가능한 증거로 푼다. 판단은 호스트가 내린다(Q-2).

## 6. 통합
- 수락된 변경은 한 체크아웃으로 모아 통합한다. 통합은 새로운 대상이므로 정책의 재검증 규칙(VER-10 `target_or_contract_change`)에 따라 필수 현재-헤드 검사를 다시 실행한다. 유효성이 입증된 증거는 VER-9에 따라 재사용할 수 있고, 라벨은 `reused`/`revalidated_from_prior_revision`으로 남긴다.
- 사용자가 명시적으로 승인하지 않는 한 push, PR 생성, 머지, 배포, 게시, 프로덕션 접근, 민감 정보 외부 전송을 하지 않는다(AUTH-4). 승인이 없으면 "머지 준비됨"으로 보고하고 멈춘다.

## 7. 정리와 마무리
- 이 작업을 위해 만든 pane·worktree·임시 자원은 더 이상 필요 없을 때 해제한다. 기존 작업과 아직 전달되지 않은 아티팩트는 보존한다.
- 마무리 보고는 다음 네 항목으로 쓴다: 완료된 것 / 검증 증거(명령·대상 리비전·결과 참조) / 미해결·미검증 항목 / 아직 유지 중인 pane과 worktree.
